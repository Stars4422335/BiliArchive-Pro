## 2026-10-20 - Task: CI 平台化修正（Linux 上失败的测试）

### 问题:
推送后 CI 红了：Ubuntu 上的 Python 3.10 / 3.12 作业失败，Windows 全绿。
失败用例是 test_security_paths.py 里的
`test_ensure_within_rejects_traversal_variants[..\..\windows\system32\config]`。

### 根因（是测试错了，不是生产代码错了）:
反斜杠在 Windows 上是路径分隔符，在 POSIX 上是**合法文件名字符**。
`base/..\..\windows\system32\config` 在 Linux 上就是一个名字很怪的文件，
路径仍在基目录内，**根本没有越界**——所以不抛 ValueError 是正确行为。
本地是 Windows，这个差异看不出来；CI 的 Linux 才暴露。

### 修复:
- 通用用例改用两个平台都是分隔符的正斜杠写法
  （../../../etc/passwd、subdir/../../../outside.txt、..、./../../outside）
- 反斜杠写法拆成带 pytest.mark.skipif(os.name != "nt") 的 Windows 专属用例
- 推送前用 posixpath 模拟 POSIX 语义验证：4 个通用用例全部拒绝、
  反斜杠用例在 POSIX 上正确地不算穿越、目录内正常路径放行

### Notes:
- **CI 红了先怀疑测试的假设，而不是生产代码**。路径穿越防护在两边都是对的，
  错的是我断言"反斜杠在任何平台都构成穿越"
- 这类平台差异本地永远查不出来——本地只有 Windows，Linux 只有 CI 有。
  已把这条与"路径测试要按平台区分""前端测试两个坑"写进 DEVELOPER_GUIDE

## 2026-10-20 - Task: 前端测试补齐 + 运维指令交互修复

### 发现并修复的真实 bug:
**「重新下载资产」的二次确认流程完全失效。**
父组件用对象记录待确认项 `setConfirming({ key: "redownload", assetId })`，
RedownloadCard 却用字符串比较 `confirming === "redownload"` —— 恒为 false，
于是用户输入编号点「重新下载」**不会有任何反应**。
即便修好比较，`confirming.assetId` 取自布尔值也恒为 undefined，
确认框显示不出编号、下发的指令也不带 asset_id。
现在待确认项直接携带编号（`confirming?.kind === "redownload"`）。

**为什么之前没发现**：重启路径用的是字符串比较，是对的，所以"看起来正常"。
只有真正驱动一次重下载交互才会暴露。

### 修复的三个真实问题:
1. **登录失效时空转 6 小时**：check_cookie 原本在凭据失效后仍返回凭据对象，
   daemon 带死 cookie 跑完整个休眠周期。新增 _is_auth_failure() 区分
   「鉴权失败」与「临时故障」：前者立即退出并提示重新登录，后者保持宽松

2. **WebUI 分不清「核心没跑」与「核心空闲」**：runtime.json 停止后仍留磁盘上，
   前端两者都显示成「等待扫描」。新增 API 字段 core_running，概览页显示
   醒目提示条 + 启动命令。判据同时看 status 与 stopped_at 标记，
   kill -9 留下的陈旧文件也不会误判。
3. **每次退出刷出看不懂的 traceback**：bilibili_api 的 atexit 清理分支写反
   （if loop.is_closed(): loop.run_until_complete(...)），导致每次正常退出
   都抛 "Event loop is closed"。关闭 loop 后置空当前事件循环，让它的
   except RuntimeError 分支安静返回。不改动第三方库。

## 2026-10-16 - Task: 安全修复 —— 专栏图片 SSRF 白名单绕过（已完成）

### 发现:
例行评估遗留缺口时扫描测试覆盖，发现 **路径穿越防护 0 处自动化测试**。
追查 _ensure_within（v1.4.0 安全加固引入，覆盖 4 处写入点）时，
发现 SSRF 域名白名单存在**真实可利用的绕过**：

    https://evil-hdslb.com/x.jpg   -> ALLOW  ← 应拒绝
    https://notbilibili.com/x.jpg  -> ALLOW  ← 应拒绝

原实现用裸 endswith 匹配白名单串，任何以 "hdslb.com" / "bilibili.com"
结尾的域名都通过。攻击者只需注册 `xxx-hdslb.com`，专栏正文里插一张
<img src="https://xxx-hdslb.com/x.jpg"> 就能让程序向其控制的服务器
发起请求。**该防护自 v1.4.0 引入起形同虚设。**

### 修复:
- 改为按标签边界匹配：域名本身，或以 "." + 受信域 开头的真子域
- 只接受 https，避免明文传输与本地探测
- 补充 bilivideo.com（B 站官方 CDN）
- 内网地址与 169.254.169.254 天然不在白名单内

### Testing:
- 新增 tests/test_security_paths.py 38 例，覆盖：
  * SSRF：真子域放行 / 伪域名拦截 / 内网与云元数据拦截 / 协议降级拦截
  * 路径穿越：.. 越界 / 绝对路径越界 / 兄弟前缀目录 / 符号链接逃逸
  * NFO 写入器确实调用路径校验，且越界时安全降级（返回 None 而非抛出）
- 全量 322 passed（284 + 38）

### Notes:
- 根因不是写错，而是**从未被验证过**。v1.4.0 安全加固当时做了
  一次性手工验证（progress.txt 记录了验证过程），但没沉淀成自动化测试。
  手工验证只能证明"当时能用"，无法防止后续回归——这正是自动化测试
  的意义所在
- 因此本次一并补齐路径穿越的测试，让两道防线都有回归保护

- 三项合计 27.99ms -> 14.03ms（2.0x）

### Notes:
**本次最重要的一次纠错——删掉自己刚加的索引。**
最初为 candidates_for_verify 建 idx_assets_verify，基线显示 10.4->3.1ms，
看似成功。但基线数据里 last_verify 全为 NULL，不具代表性。
用真实分布复测后发现三种填充率下全部更慢：
  0%   填充: 6.37 -> 13.88ms（慢 2.2x）
  50%  填充: 5.70 -> 18.10ms（慢 3.2x）
  100% 填充: 11.34 -> 108.37ms（慢 9.6x）
原因：其排序键 ORDER BY last_verify IS NOT NULL 也是表达式，SQLite 用不上
索引排序，反而要为每个匹配行回表取 last_verify 再排临时 B-tree。
教训：索引收益高度依赖数据分布，用失真的基线做决策会得到相反结论。

- 刻意不优化 candidates_for_verify：它每 6 小时才跑一次，不在交互路径上，
  而 WebUI 是用户每次打开都要用的。优化交互路径优先
